## 2. 技术目标与约束

### 2.1 技术目标

1. 使用一套主要开发语言覆盖 Mini App、API、Bot 和管理后台。
2. 视频不经过 VPS 存储和代理，由 Telegram 原生播放器承担播放。
3. 图片按需从 Telegram 获取并流式转发，不永久保存于 VPS。
4. 作品目录根据真实内容、发布状态和权限动态生成。
5. 关键业务操作可追踪、可重试且具有幂等性。
6. 以单台 VPS 完成 MVP 部署，并保留后续拆分能力。
7. 实施会员开关、公开或会员两级内容权限及个性化推荐。

### 2.2 硬性约束

- Mini App 必须通过 HTTPS 提供。
- Bot Token 不得进入浏览器环境。
- Telegram 云端 Bot API `getFile` 当前只支持下载不超过 20MB 的文件。
- Telegram 文件下载地址包含 Bot Token，不能直接返回给 Mini App。
- 面向用户发送的媒体消息必须在发送时启用内容保护。
- 视频消息不创建自动删除任务。
- 多个视频版本存在时默认选择最高分辨率版本。
- Telegram 原生播放器不向业务系统提供真实播放进度。
- Bot API 对普通消息删除存在时间窗口，不能把历史消息撤回作为长期权限保障。
- 漫画内容不允许关联视频内容单元。
- 图片源文件不得通过 Bot 分发给用户。
- Telegram Premium 4GB 视频的 `copyMessage + protect_content` 链路已在过往项目完成验证，当前项目将该结论作为已确认技术输入。

### 3.2 选择 TypeScript 的原因

- 前后端和 Bot 共用内容模型与接口契约。
- grammY、React、NestJS 和 Telegram WebApp API 的生态成熟。
- 当前视频不经过服务端，Node.js 的计算性能满足业务需求。
- 降低同时维护 Python 和 TypeScript 两套业务模型的成本。

Python 可用于未来的批量媒体检查或辅助脚本，但不作为核心在线服务语言。

### 3.3 明确不采用的首版技术

- Next.js 或服务端渲染：Mini App 不需要 SEO，Vite SPA 更简单。
- MTProto 流媒体网关：已确定使用 Telegram 原生播放器。
- HLS 视频服务：首版没有 Mini App 内嵌播放器。
- 本地 Bot API Server：首版图片限制在云端 `getFile` 支持范围内，视频不下载。
- 对象存储：首版媒体源使用 Telegram；数据库备份不受此限制。
- Kubernetes：单台 VPS 的 MVP 不需要该复杂度。

### 4.1 服务边界

#### Mini App

- Telegram 身份初始化。
- 首页、分类、搜索和作品详情。
- 动态内容分区。
- 图集和漫画阅读。
- 收藏、阅读进度和视频发送请求。

#### API

- 验证 Telegram `initData`。
- 签发短时效业务会话。
- 提供目录、作品、内容和权限接口。
- 创建视频分发任务。
- 流式代理 Telegram 图片。
- 提供管理后台接口。

#### Bot Worker

- 接收 Telegram Webhook。
- 处理私有频道的资源入库事件。
- 消费视频分发任务。
- 使用 `copyMessage` 或必要时使用 `sendVideo(file_id)`。
- 处理上一集、下一集和重新选集按钮。
- 不创建视频消息自动删除任务。

#### 管理后台

- 作品、分区、内容单元和媒体关联管理。
- 资源入库编排。
- 发布状态和访问权限管理。
- 用户、发送记录和审计查询。
- 具备发布权限的单个管理员直接审核和发布内容。
- 通过 Bot 向白名单管理员提供专用 Web App 入口，在 Telegram 内使用经过后端验证的 `initData` 登录；首版不支持独立浏览器登录。

## 6. 领域模型

### 6.1 用户与权限

#### users

- 内部用户 ID。
- Telegram User ID，唯一。
- 用户名、显示名、语言和头像信息。
- 用户状态：正常、冻结、删除。
- 会员状态和会员有效期。
- Bot 会话建立时间、最近可发送状态、状态检测时间和最近不可发送原因。
- 首次登录和最后活动时间。

#### system_settings

- 全局会员权限开关。
- 推荐参数版本。
- 会员开通说明、人工服务入口和 `membership_cta` 版本。
- 当前测试或生产环境标识。
- 修改管理员和修改时间。

#### entitlements

- 用户 ID。
- 权限作用域：全局、作品、分区或内容单元。
- 权限类型。
- 生效时间和失效时间。
- 来源和备注。

首版以会员状态作为默认全局权限：有效会员可访问全部已发布内容，普通用户只能访问 `public` 内容。细粒度授权表保留给特殊授权场景。

#### admin_accounts / admin_roles

- 管理员 Telegram User ID。
- 角色和权限集合。
- 状态和最后登录时间。

### 6.2 内容模型

#### works

- 作品 ID。
- 主类型：`video`、`comic`、`gallery`、`photoshoot`。
- 子类型：电影、电视剧、短剧、普通图集等。
- 名称、别名、简介、封面资源 ID。
- 通用可选资料：原名、别名、简介、地区或国家、发行年份、发行日期、语言、标签、发行状态和分级。
- 影视可选资料：导演、演员、编剧、制片人、出品方、总集数和时长。
- 漫画可选资料：作者、原作、作画、出版社、连载平台和连载状态。
- 图集或写真可选资料：摄影师、模特或主体、工作室、拍摄日期、地点和辑数。
- 发布状态 `publication_status`：草稿、已发布、已下架。
- 可选发行状态 `release_status`：未上映、连载中、已完结等业务资料值。
- 可选访问级别 `access_level`：`public` 或 `member`；未设置时默认为 `public`。
- 排序和发布时间。

所有资料字段在数据库中允许为 `NULL`。API 展示层将空值规范化为“未知”，不使用字符串“未知”污染原始数据。

#### content_sections

- 分区 ID 和作品 ID。
- 分区类型：播放、选集、剧照、漫画目录、图集、写真、花絮。
- 显示标题和排序。
- 发布状态 `publication_status`。
- 可选访问级别 `access_level`：`public` 或 `member`；未设置时继承作品。

分区表保存编排信息，但前端是否显示仍由分区内实际可见内容计算得出。

#### content_units

- 内容单元 ID 和分区 ID。
- 类型：电影、剧集、短片、漫画章节、图片集、写真集、花絮视频。
- 标题、序号、季号、集号或章节号。
- 简介、封面和排序。
- 发布状态 `publication_status`。
- 可选访问级别 `access_level`：`public` 或 `member`；未设置时先继承分区，再继承作品。

#### media_assets

- 媒体资源 ID。
- 所属内容单元或作品。
- 类型：视频、图片、缩略图、封面、文件。
- 角色：正片、剧照、漫画页、写真页、花絮、海报等。
- Telegram 存储频道 ID。
- Telegram 源消息 ID。
- `file_id` 和 `file_unique_id`。
- 文件名、MIME、大小、宽高和时长。
- 视频版本标识、像素数和管理员主版本标记。
- 图片逻辑资源 ID、父资源 ID和版本角色：`source`、`browse` 或 `thumbnail`。
- 页序或资源顺序。
- 状态：待编排、可用、失效、下架。

`storage_chat_id + source_message_id` 是 Telegram 源消息的主要定位依据；`file_id` 用于 Bot API 文件复用或图片获取。

同一逻辑图片可以对应多个 `media_assets`。`source` 只用于受控管理和归档；`browse` 是 Mini App 放大查看使用的合规版本；`thumbnail` 用于列表和首屏。会员锁定作品卡片使用的封面必须是单独标记为公开展示的资源，不能复用会员图片地址。

#### content_relations

- 来源作品或内容单元。
- 目标作品或内容单元。
- 关系类型：对应剧照、对应花絮、补充图片等。
- 排序。

### 6.3 用户行为

#### favorites

- 用户 ID 和作品 ID。
- 收藏时间。
- 用户和作品组合唯一。

#### reading_progress

- 用户 ID 和内容单元 ID。
- 进度类型：漫画或图集。
- 当前页、总页数或滚动锚点。
- 阅读方式、页面布局和阅读方向。
- 最近更新时间。

#### content_events

- 用户 ID、作品 ID和可选内容单元 ID。
- 行为类型：展示、点击、收藏、取消收藏、阅读、重复访问、请求发送。
- 行为权重、发生时间和推荐请求 ID。
- 事件来源：服务端业务事实或经过校验的客户端展示/点击。
- 幂等键、算法版本和可选展示位。

不记录 Telegram 原生播放器的虚构播放完成事件。

收藏、取消收藏、阅读进度和请求发送由对应业务接口在服务端生成事件，客户端不能直接伪造。`POST /events/content` 只接受展示和点击事件，并要求推荐请求 ID、结果归属校验、幂等去重和独立速率限制。原始事件保留 180 天，聚合画像按用户状态更新；账号删除后 30 天内删除或匿名化相关行为数据。

#### user_interest_profiles

- 用户 ID。
- 主类型、标签和内容主题权重。
- 最近更新和算法版本。
- 冷启动偏好状态。

#### media_deliveries

- 分发请求 ID。
- 用户、作品、内容单元和媒体资源 ID。
- 源频道 ID 和源消息 ID。
- 目标聊天 ID和目标消息 ID。
- 状态：排队、发送中、成功、失败。
- `protect_content` 状态。
- 幂等键。
- Telegram 错误码、错误描述和重试次数。
- 创建和发送时间。

#### ingestion_items

- Telegram 存储频道消息信息。
- 媒体元数据。
- 入库状态：待处理、已关联、忽略、失败。
- 操作管理员和时间。

#### admin_audit_logs

- 管理员 ID。
- 操作类型和目标对象。
- 修改前后摘要。
- 请求 ID、IP 和时间。

### 6.4 业务约束

- `video` 作品允许视频单元和剧照图集。
- `comic` 作品只允许漫画章节和图片资源，不允许视频单元。
- `gallery` 作品以普通图片集为主。
- `photoshoot` 作品允许写真图集和花絮视频。
- 会员权限关闭时跳过内容会员级别检查；开启时普通用户只能访问 `public` 内容。
- 有效访问级别按“内容单元显式值 -> 分区显式值 -> 作品显式值 -> `public` 默认值”计算，最接近资源的显式值优先。
- 作品发现权限与媒体访问权限分离：普通用户可发现锁定会员作品，但只获得安全基础资料、公开展示封面、会员标识和购买入口。
- 图片源文件不建立面向用户的 Bot 分发操作。
- 视频分发从可用版本中选择像素数最高的版本；像素数相同时选择管理员主版本。
- 已发布内容单元必须至少包含一个可用媒体资源。
- 同一漫画章节内的页序必须唯一且连续性可检查。
- 同一源频道消息不得被重复登记为不同的物理媒体来源，业务复用通过关联实现。

跨表内容组合约束由领域服务在事务内验证；数据库使用唯一索引、外键和状态检查约束保证基础完整性。

## 7. 动态目录算法

服务端生成作品详情时：

1. 检查作品发布状态；未发布或已下架作品对普通用户不可发现。
2. 读取全局会员权限开关和当前用户会员状态。
3. 计算作品有效访问级别和 `access_granted`。
4. 当普通用户访问锁定会员作品时，返回锁定作品 DTO：安全基础资料、公开展示封面、会员标识和购买入口；不查询或返回分区、内容单元、资源数量、媒体地址和分发能力。
5. 对可访问作品查询已配置分区，并按作品主类型过滤不允许的分区类型。
6. 逐项计算分区和内容单元有效访问级别；会员开关开启时过滤普通用户无权访问的 `member` 内容。
7. 过滤结果为空的分区，按后台配置顺序返回最终分区及内容摘要。
8. 会员权限开关关闭时跳过会员过滤，所有已发布内容视为可访问，并隐藏会员锁定状态和购买入口。

不得把 `has_comic`、`has_photoshoot` 等人工维护布尔值作为事实来源。可以建立缓存或物化统计字段，但必须可由真实内容重新计算。

### 7.1 个性化推荐与排行榜

MVP 使用可解释的加权排序，不在首版引入离线机器学习平台。基础得分由以下部分组成：

- 用户主类型和标签亲和度。
- 收藏、阅读、重复访问和视频请求发送行为权重。
- 内容新鲜度和全局热度。
- 已经频繁展示或明确取消收藏的降权。
- 当前用户权限过滤。

`content_events` 通过后台任务聚合到 `user_interest_profiles`。推荐结果记录算法版本和推荐请求 ID，用于计算点击与后续行为。冷启动用户使用主动偏好、整体热度和最近更新。普通用户的推荐和排行榜可以包含锁定会员作品卡片，用于会员转化，但响应只携带锁定作品 DTO，绝不携带会员文件、目录明细或媒体访问能力。

## 8. API 设计

### 8.1 协议约定

- 使用 HTTPS REST JSON API。
- 通过 OpenAPI 生成接口说明和客户端类型。
- 所有响应包含请求 ID。
- 业务错误使用稳定错误码，不直接把 Telegram 或数据库内部异常暴露给前端。
- 列表接口使用游标分页；管理后台小列表可使用页码分页。

### 8.2 身份接口

- `POST /auth/telegram`：验证 Mini App `initData` 并建立业务会话。
- `POST /auth/refresh`：刷新短时效会话。
- `POST /auth/logout`：注销当前会话。
- `GET /me`：返回当前用户和权限摘要。

### 8.3 内容接口

- `GET /works`：作品列表、分类和筛选。
- `GET /works/search`：关键词搜索。
- `GET /works/{workId}`：作品详情和动态分区。
- `GET /recommendations`：当前用户个性化推荐。
- `GET /rankings`：当前用户个性化排行榜。
- `GET /sections/{sectionId}/units`：内容单元列表。
- `GET /units/{unitId}`：章节、剧集或图集详情。
- `GET /units/{unitId}/images`：按序返回签名图片资源摘要。

作品列表和详情统一返回 `access_granted`、`access_level` 和可选 `membership_cta`。锁定作品响应使用独立 Schema，并禁止出现 `sections`、`units`、资源数量、媒体 URL、图片签名和视频分发参数。混合权限作品只返回当前用户可访问的分区和单元。

`membership_cta` 使用受控 Bot 深链接和短来源标识，打开会员开通说明或人工服务流程。MVP 不创建订单或支付接口；管理员确认完成后通过管理后台手动设置会员状态和有效期。

### 8.4 用户行为接口

- `GET /favorites`：收藏列表。
- `PUT /favorites/{workId}`：收藏作品。
- `DELETE /favorites/{workId}`：取消收藏。
- `PUT /reading-progress/{unitId}`：保存漫画或图集进度。
- `GET /history`：阅读记录和最近发送。
- `POST /events/content`：只记录经过推荐结果归属校验的展示和点击事件；收藏、阅读和发送行为由服务端业务接口生成。

### 8.5 视频分发接口

- `POST /deliveries/video`：为指定内容单元创建发送任务。
- `GET /deliveries/{deliveryId}`：查询发送状态。

创建分发任务时必须验证：

- 用户状态正常。
- 作品和内容单元已发布。
- 当前用户具备访问权限。
- 媒体资源状态可用。
- 系统已经从可用版本中选择最高分辨率视频。
- 用户未超过并发或频率限制。
- 相同幂等键未创建重复任务。

### 8.6 图片媒体接口

- `GET /media/images/{assetId}`：验证签名后流式返回图片。
- `GET /media/thumbnails/{assetId}`：返回缩略图。

签名至少绑定资源 ID、用户或权限摘要、失效时间和签名版本。日志必须隐藏完整签名参数。

### 8.7 管理接口

- 作品、分区、内容单元和媒体资源 CRUD。
- 待入库资源列表和关联操作。
- 发布、下架和排序。
- 会员权限开关、用户会员状态和内容访问级别管理。
- 单管理员审核和发布；发布动作必须写入审计日志。
- 分发记录、任务和审计日志查询。

管理接口统一位于 `/admin` 命名空间并实施角色权限控制。

### 8.8 管理员身份

- Bot 仅向 `admin_accounts` 白名单中的有效管理员返回专用 `web_app` 按钮。
- 管理后台作为独立 React 应用部署，但 MVP 只允许在 Telegram Web App 容器内打开。
- 管理前端提交原始 `initData` 到现有 `POST /auth/telegram`，后端完成签名、时效、管理员状态和角色校验后签发管理会话。
- 管理会话使用独立受众、较短有效期和更严格的刷新策略，不能与普通用户令牌互换。
- 直接在普通浏览器打开管理域名时不建立会话；首版不接入 Telegram Login Widget 或其他独立浏览器登录方案。

## 9. Telegram Mini App 集成

### 9.1 初始化

- 前端通过 Telegram WebApp JavaScript API 获取原始 `initData`。
- 后端严格按照 Telegram 官方算法验证签名。
- 校验 `auth_date`，默认只接受可配置的短时间窗口。
- 可在 Redis 中短期记录已使用签名摘要，降低重放风险。
- 验证成功后同步或创建用户，并签发短时效业务令牌。

前端展示数据不得被用作身份事实，特别是 `initDataUnsafe.user` 不能替代后端签名验证。

### 9.2 WebApp 能力封装

在前端建立单一适配层，封装：

- `ready` 和 `expand`。
- BackButton。
- 主题和颜色参数。
- 安全区域与动态视口。
- 垂直滑动控制。
- 打开 Telegram 链接和关闭 Mini App。

所有能力调用先进行版本和可用性检查，非 Telegram 浏览器环境使用开发模拟器。

### 9.3 深链接

作品和内容单元使用 `startapp` 参数生成 Mini App 深链接。服务端只接受短内部标识或签名参数，不在深链接中放置权限信息、Bot Token 或 Telegram 文件路径。

## 10. Bot 集成

### 10.1 Webhook

- 生产环境使用 Webhook，开发环境可使用 Long Polling。
- Webhook 使用不可猜测路径和 Telegram Secret Token Header。
- 更新先快速确认，再将耗时任务提交至 BullMQ。
- 更新 ID 用于去重，避免 Telegram 重试导致重复处理。

### 10.2 存储频道入库

1. Bot 作为管理员加入私有存储频道。
2. 管理员使用 Telegram 客户端上传资源。
3. Bot 接收 `channel_post` 更新。
4. 提取频道 ID、消息 ID、媒体类型、`file_id`、`file_unique_id` 和文件元数据。
5. 创建待编排入库记录。
6. 管理员在后台将资源关联到内容单元。
7. 具备发布权限的管理员独立检查并发布，不等待第二人审批。

Bot 只能可靠处理加入后收到的更新。历史消息需要通过专用导入流程或管理员重新转发登记。

### 10.3 用户会话与可发送状态

- Bot 在收到用户 `/start` 时记录 `bot_started_at` 和最近可发送状态；`/start` 参数只保存短内部跳转标识。
- Mini App 创建视频任务前检查最近可发送状态。尚未启动 Bot 时返回稳定错误码和带原作品跳转参数的 Bot 深链接，不创建队列任务。
- Telegram 返回 Bot 被屏蔽或目标聊天不可用时，更新用户可发送状态，任务直接失败且不进行无限重试。
- 用户完成 `/start` 或解除屏蔽后可以重试；重试必须重新校验会员、内容发布状态和媒体可用性。
- 缓存状态只用于提前提示，实际发送结果始终以 Telegram Bot API 返回为准。

### 10.4 视频分发

创建发送任务前，按 `width * height` 从当前内容单元的可用视频版本中选择最高分辨率；像素数相同时使用管理员标记的主版本。

默认使用 `copyMessage`：

- 来源为私有存储频道和源消息 ID。
- 目标为用户与 Bot 的私聊。
- 设置 `protect_content=true`。
- 可覆盖标题并附加内联按钮。
- 保存返回的目标消息 ID。

如果资源适合通过 `file_id` 复用，可使用 `sendVideo(file_id)`，但仍必须设置内容保护。Telegram Premium 4GB 视频的 `copyMessage + protect_content` 以及 iOS、Android、Desktop 原生播放链路已在过往项目验证通过，本项目将其作为已确认技术基线，不再列为可行性阻断项。Staging 上线前仍使用 4GB 样本执行一次冒烟回归，用于发现当前 Bot、频道或客户端环境配置回归；若失败，按环境缺陷处理并阻止该环境上线，不推翻既有技术结论。

默认兼容规格为 MP4 容器、H.264/AVC 视频、AAC-LC 音频、`yuv420p` 像素格式和 fast-start。服务端不进行实时转码，不符合规格的资源在入库时标记为不可发布。

### 10.5 消息按钮

视频消息可提供：

- 上一集和下一集回调。
- 打开 Mini App 选集页。
- 收藏或打开作品详情。

回调只携带短内部标识。收到回调后重新检查权限，不信任旧按钮代表的历史权限。

### 10.6 限流、幂等与重试

- 分发幂等键建议由用户 ID、内容单元 ID 和短时间窗口组成。
- 捕获 Telegram `429` 并遵循 `retry_after`。
- 网络错误使用有上限的指数退避。
- 权限、资源不存在和 Bot 被用户阻止等错误不进行无限重试。
- 同一用户限制同时进行的发送任务数量。

### 10.7 保护与消息保留

- `protect_content` 必须在发送时设置，不能事后编辑补加。
- 系统不创建或调度视频消息自动删除任务。
- 用户权限到期后立即禁止新的会员内容访问和发送。
- 已经发送成功的视频消息继续保留在用户私聊中。
- `protect_content` 只限制官方客户端中的转发和保存，不作为 DRM 或到期撤回机制。

## 11. 图片获取与代理

### 11.1 入库约束

- Mini App 图片浏览版本遵守 Bot API `sendPhoto` 当前上限：最大 10MB、宽高之和不超过 10000、宽高比不超过 20。
- Telegram 图片源文件可以保留在私有频道；管理员必须在本地预先生成符合上述限制的浏览版本和必要缩略图，再分别上传到私有频道。
- 源文件超过云端 `getFile` 20MB 上限时，服务端永远不尝试下载源文件后转换，只读取管理员预先上传的浏览版本。
- 漫画正文优先以 `document` 保存，避免 Telegram 照片压缩影响文字。
- 同时保存 Telegram 返回的多个 `PhotoSize` 或配套预览图，用于列表和快速首屏。
- 保存原始文件名和 MIME，因为 `getFile` 不保证完整保留这些信息。
- 不为图片源文件创建面向用户的 Bot 发送或复制接口。

### 11.2 图片版本编排与发布门槛

1. 管理员在本地从源图生成最大 10MB、宽高之和不超过 10000、宽高比不超过 20 的 `browse` 版本，并根据列表用途生成 `thumbnail`。
2. 管理员将 `source`、`browse` 和 `thumbnail` 分别上传到私有频道；Bot 为每条消息创建入库记录。
3. 管理员在后台把这些记录关联到同一图片逻辑资源，设置版本角色、页序和对应作品或内容单元。
4. 发布校验确认每一页至少有一个可由云端 `getFile` 获取的 `browse` 版本，MIME、大小和尺寸均符合约束；列表需要缩略图时同时校验 `thumbnail`。
5. 校验失败的图片页或内容单元保持草稿状态并显示具体原因，不能绕过发布门槛。

MVP 不在 VPS 上提供图片转码服务，不保存转换临时文件。未来若引入临时转换 Worker，必须另行评审资源隔离、临时文件销毁和大文件获取方案。

### 11.3 请求流程

```text
Mini App
  -> 带短时签名的内部图片 URL
  -> API 校验用户和资源权限
  -> Redis 查询有效 file_path 缓存
  -> 必要时调用 getFile
  -> 服务端从 Telegram 读取并流式转发
  -> 客户端显示
```

- Telegram 下载 URL 只在服务端使用。
- `file_path` 缓存时间应短于 Telegram 保证有效期。
- 数据采用流式转发，避免完整图片进入进程内存。
- 客户端断开时中止上游请求。
- 首版不在 VPS 永久缓存图片字节。

### 11.4 HTTP 行为

- 返回正确的 `Content-Type`、`Content-Length` 和缓存策略。
- 权限相关图片默认采用私有缓存策略。
- 不把上游 Telegram 错误页面作为图片返回。
- 对超大、损坏或 MIME 不允许的文件返回稳定业务错误。
- 限制每个用户的并发图片请求数量。
- 根据客户端视口宽度、设备像素比和当前用途选择最接近的预览尺寸；放大查看时再请求浏览版本。

### 11.5 图片保护边界

Mini App 图片必须传输到浏览器才能显示，因此无法完全阻止截图、缓存或设备级抓取。技术措施只包括：

- 短时签名。
- 用户与内容权限校验。
- 防盗链和速率限制。
- 不暴露 Telegram 文件地址和 Bot Token。
- 可选的用户级水印属于后续功能。

## 12. Mini App 前端实现

### 12.1 数据与状态

- TanStack Query 管理作品、目录、图集、收藏和发送状态。
- Zustand 仅管理阅读模式、控件显隐等短期客户端状态。
- 阅读进度进行防抖保存，并在页面隐藏、退出阅读器和切换章节时立即提交。
- API 契约从共享 Zod Schema 派生，禁止手工维护重复类型。

### 12.2 普通图集

- 缩略图网格使用响应式稳定尺寸，防止图片加载造成布局跳动。
- PhotoSwipe 负责全屏、缩放、拖动和切换。
- 根据视口宽度和设备像素比请求最接近的 Telegram `PhotoSize` 或配套预览图。
- 只预取当前图片附近资源。
- 原图加载失败时保留预览并提供重试。

### 12.3 漫画阅读器

- 使用浏览器原生滚动、IntersectionObserver 和图片懒加载。
- 连续滚动模式不一次挂载全部高分辨率图片。
- 分页模式维护明确页索引和缩放状态。
- 放大状态下优先处理图片拖动，未放大时才处理翻页手势。
- 双页模式仅在宽度允许时启用，窄屏自动回退单页并保留用户偏好。
- 进度以稳定页索引为主，滚动锚点为辅。

### 12.4 GSAP 使用边界

GSAP 用于：

- 页面进入和退出。
- 阅读器控制栏显隐。
- 目录展开、状态切换和轻量反馈。

GSAP 不用于：

- 接管原生长列表滚动。
- 图片缩放核心逻辑。
- 持续运行的大面积装饰动画。

动画优先使用 `transform` 和 `opacity`，尊重 `prefers-reduced-motion`，并在 React 组件卸载时清理上下文。

### 12.5 可访问性

- 图标按钮提供可读标签和工具提示。
- 控件具备足够点击区域。
- 状态不只依赖颜色表达。
- 图片提供合理替代文本；漫画页可使用章节和页码描述。
- 动画可减弱或关闭。

## 13. 后台任务设计

### 13.1 队列

建议至少建立：

- `telegram-delivery`：媒体发送。
- `media-reconcile`：资源元数据和失效状态检查。
- `interest-profile`：聚合用户偏好并更新推荐画像。
- `audit-export`：后续审计导出。

### 13.2 任务要求

- 每个任务具有唯一 ID 和幂等键。
- 明确最大重试次数、退避策略和不可重试错误。
- 任务状态与业务记录同步。
- Worker 重启后未完成任务可恢复。
- Redis 开启持久化或使用可靠托管实例，避免任务静默丢失。

## 14. 安全设计

### 14.1 密钥管理

- Bot Token、数据库密码、Redis 密码和签名密钥通过环境变量或密钥文件注入。
- 不写入仓库、前端包、日志和错误响应。
- 支持密钥轮换和签名版本迁移。

### 14.2 访问控制

- 用户接口验证业务会话和资源权限。
- 会员开关开启时，所有作品、分区、单元、图片签名和视频发送请求统一执行 `public/member` 权限判断。
- 对作品执行权限判断时同时返回 `access_granted`，不隐藏已发布会员作品的安全发现信息；对分区、单元、图片和视频分发则执行严格媒体访问过滤。
- 管理接口同时验证管理员身份和角色权限。
- Bot 回调重新验证权限。
- 存储频道只允许受控管理员和 Bot。

### 14.3 接口防护

- 对登录、搜索、图片和视频发送接口分别限流。
- 限制请求体大小和允许的 Content-Type。
- CORS 仅允许配置的 Mini App 和管理后台域名。
- 使用安全响应头，管理后台禁止被任意站点嵌入。
- 图片签名和 Telegram `initData` 摘要不得完整写入访问日志。

### 14.4 审计

记录：

- 登录和鉴权失败。
- 媒体发送请求及结果。
- 权限授予和撤销。
- 作品发布和下架。
- 媒体关联和删除。
- 管理员角色变化。

## 15. 部署方案

### 15.1 MVP 服务器

建议初始配置：

```text
2 vCPU
4 GB RAM
40-80 GB SSD
100 Mbps 或更高网络端口
每月不少于 1 TB 可用流量
```

视频流量由 Telegram 承担。VPS 主要负载为 API、图片代理、数据库、Redis 和 Bot 消息任务。

该规格对应以下容量基线：累计注册用户 10,000、日活用户 1,000、峰值在线用户 100、作品 5,000、内容单元 50,000、媒体元数据 500,000 条、核心 API 峰值 50 RPS、图片代理峰值 10 个并发流。该基线是工程验收负载，不是业务增长预测；容量达到任一基线的 70% 时执行扩容评估。

上线前必须在同拓扑 Staging 完成 50 RPS 核心 API 和 10 个并发图片流各持续 15 分钟的测试。若 P95、错误率或资源水位不达标，生产配置升级至至少 `4 vCPU / 8GB RAM`，或拆分 PostgreSQL、Redis 和图片代理后重新测试，不能仅凭建议配置上线。

### 15.2 Docker Compose 服务

- `caddy`
- `api`
- `bot-worker`
- `postgres`
- `redis`
- Mini App 静态文件
- 管理后台静态文件

PostgreSQL 和 Redis 使用独立持久卷。VPS 不创建影视媒体持久卷。

### 15.3 域名与路由

建议拆分：

- Mini App 域名。
- 管理后台域名。
- API 域名或 Mini App 同源 `/api`。
- Telegram Webhook 使用独立受保护路径。

Caddy 负责 TLS、压缩、安全响应头和反向代理。

### 15.4 环境

- `development`：Telegram API 模拟器或测试 Bot、Long Polling。
- `staging`：独立测试 Bot、测试存储频道、测试域名、PostgreSQL 和 Redis。
- `production`：正式 Bot、正式私有频道和生产数据库。

测试与生产不得共享 Bot Token、存储频道或数据库。

正式域名、Bot 和私有存储频道已由产品侧准备。最优测试环境使用独立 VPS，建议 `2 vCPU / 4GB RAM / 40GB SSD`，运行与生产相同的 Docker Compose 拓扑；使用独立 HTTPS 子域名、测试 Bot、测试频道、数据库卷和 Redis 卷。Staging 不接触生产用户或生产媒体记录。

## 16. 可观测性与备份

### 16.1 日志

所有服务使用结构化日志并包含：

- 请求 ID。
- 用户内部 ID；避免不必要记录完整个人资料。
- 任务 ID和分发 ID。
- Telegram 方法和脱敏错误信息。
- 响应时间和结果状态。

### 16.2 指标

重点指标：

- API 请求量、错误率和延迟。
- 图片代理流量、错误率和上游耗时。
- Bot 发送成功率、失败率和 `429` 数量。
- BullMQ 队列长度、等待时间和失败任务。
- PostgreSQL 连接、慢查询和存储增长。
- Redis 内存和命中率。

MVP 告警与验收阈值：

- 核心 API P95 不高于 500ms，5 分钟窗口服务端错误率低于 1%。
- 视频请求接口在 500ms 内返回排队结果；排除用户未启动或屏蔽 Bot、资源失效和 Telegram 平台故障后，发送成功率不低于 98%，P95 队列等待不高于 10 秒。
- 图片代理 P95 首字节时间不高于 1.5 秒，5 分钟窗口错误率低于 1%。
- 负载测试期间 CPU 持续低于 75%，内存持续低于 80%，队列无持续增长。
- 月度业务服务可用性目标为 99.5%，Telegram 平台中断单独记录。

### 16.3 备份

- PostgreSQL 每日自动备份。
- 备份文件加密并存放在 VPS 之外。
- PostgreSQL RPO 为 24 小时、RTO 为 4 小时；至少每季度执行一次恢复演练。
- Redis 开启 AOF 持久化并监控任务恢复；业务记录以 PostgreSQL 为准，队列恢复后执行任务状态对账。
- Telegram 媒体不进入数据库备份，只备份定位信息和业务元数据。

### 16.4 数据保留

- 推荐原始行为事件保留 180 天，超过期限批量删除；聚合兴趣画像按用户最后活动时间持续更新。
- 应用运行日志保留 30 天，鉴权与安全日志保留 90 天，管理员审计日志保留 365 天。
- 用户账号删除后 30 天内删除或匿名化行为事件与兴趣画像；必须保留的安全审计记录只保留最小必要标识。
- 保留任务由队列定期执行，执行数量、失败数量和删除数量进入监控。

## 19. 主要风险与处理

| 风险 | 影响 | 处理方式 |
|---|---|---|
| Telegram 服务或限流 | 视频发送延迟或失败 | BullMQ、幂等、`retry_after`、明确失败状态 |
| `protect_content` 不是 DRM | 仍可能录屏或设备级复制 | 产品明确边界、限制转发保存、控制单次发送 |
| 视频消息不自动删除 | 会员到期后历史消息仍可播放 | 作为已确认产品行为；到期只禁止新的访问和发送 |
| Bot 原生播放器无进度事件 | 无法精确续播 | 只展示最近发送，不伪装为精确进度 |
| 图片超过 Telegram 浏览边界 | Mini App 无法获取或显示 | 生成最大 10MB 且满足尺寸约束的浏览版本，源文件不向用户下发 |
| 图片代理流量增长 | VPS 带宽和连接压力 | 预览图、懒加载、并发限制，必要时引入 CDN |
| 存储频道消息被删除 | 资源失效 | 管理权限最小化、定期一致性检查、失效告警 |
| 4GB 当前环境配置回归 | 已验证链路可能因 Bot、频道或客户端环境变化失败 | 复用过往验证结论，Staging 使用真实 4GB 样本冒烟；失败按环境缺陷处理并阻断该环境上线 |
| 空分区或权限泄漏 | 用户看到无效入口 | 服务端动态目录统一计算，前端不自行推断 |

## 20. 技术决策记录

### ADR-001：全栈 TypeScript

状态：接受。统一前后端和 Bot 开发语言，减少共享模型维护成本。

### ADR-002：Telegram 原生视频播放

状态：接受。放弃首版 Mini App 内嵌播放器、HLS 和 MTProto 网关，降低 VPS 存储与带宽成本。

### ADR-003：Telegram 私有频道作为媒体来源

状态：接受。视频通过消息复制分发；图片通过受控服务端代理读取。

### ADR-004：动态内容分区

状态：接受。目录从已发布且有权限的真实内容计算，不维护人工 `has_*` 事实字段。

### ADR-005：模块化单体加独立 Worker

状态：接受。API 与 Bot Worker 分进程部署，共享数据库和契约，满足 MVP 并保留拆分空间。

### ADR-006：会员开关与两级访问权限

状态：接受。全局会员开关开启时，有效会员访问全部已发布内容，普通用户只能访问 `public` 内容；关闭时不执行会员内容限制。

### ADR-007：视频消息永久保留

状态：接受。不创建自动删除任务；会员失效只阻止新的会员内容访问和发送。

### ADR-008：最高分辨率视频与已验证 4GB 链路

状态：接受。从已上传可用版本中自动选择最高分辨率，使用 MP4/H.264/AAC-LC 兼容规格。Telegram Premium 4GB 文件的复制、内容保护和原生播放链路已在过往项目验证通过，本项目复用结论并在 Staging 做环境冒烟回归。

### ADR-009：个性化推荐与排行榜

状态：接受。首版使用基于用户类型、标签、收藏、阅读、视频发送、内容热度和新鲜度的可解释加权算法。

### ADR-010：图片浏览边界与禁止源文件下发

状态：接受。图片浏览版本遵守 Telegram `sendPhoto` 当前 10MB 及尺寸边界，预览尺寸按客户端自适应选择，不提供 Bot 图片源文件分发。

### ADR-011：单管理员发布与可选作品资料

状态：接受。具备发布权限的单个管理员可完成审核发布；作品扩展资料允许为空，展示层统一显示“未知”。

### ADR-012：会员作品可发现但媒体隔离

状态：接受。普通用户可以在目录、搜索、推荐和排行榜中看到会员作品的安全基础资料、公开展示封面、会员标识和购买入口；服务端不返回会员分区、内容单元、媒体地址或分发能力。

### ADR-013：三级权限继承

状态：接受。`works`、`content_sections` 和 `content_units` 均支持可选 `access_level`；有效值按内容单元、分区、作品、公开默认值的顺序解析，子级显式值覆盖父级。

### ADR-014：管理员 Telegram Web App 登录

状态：接受。MVP 管理后台通过 Bot 的管理员专用 Web App 入口在 Telegram 内打开，使用已验证 `initData`、管理员白名单和角色权限登录；不提供独立浏览器登录。

### ADR-015：管理员本地生成图片浏览版本

状态：接受。管理员在上传前生成 `browse` 和 `thumbnail` 版本，分别存入 Telegram 并与 `source` 关联；VPS 不承担图片转码或永久存储。

## 21. 已确认开发基线

1. 提供全局会员权限开关。开关开启时，有效会员可访问所有已发布文件，普通用户不能访问 `member` 文件；关闭时所有已发布内容按公开内容处理。
2. 视频消息不进行自动删除，系统不创建 `telegram-delete` 队列或删除调度。
3. 视频选择最高分辨率的已上传版本；目标最大测试文件为 Telegram Premium 4GB，默认规格为 MP4、H.264/AVC、AAC-LC、`yuv420p` 和 fast-start。
4. 图片浏览版本采用 Telegram `sendPhoto` 当前最大 10MB、宽高之和不超过 10000、宽高比不超过 20 的边界；预览图按客户端视口和设备像素比自适应匹配。
5. 作品资料字段采用需求文档第 11.4 节定义的完整可选集合，数据库空值由展示层显示为“未知”。
6. 正式域名、正式 Bot 和正式私有存储频道已准备；测试环境采用独立 VPS、测试域名、测试 Bot、测试频道、PostgreSQL 和 Redis，不与生产共享凭据或数据。
7. 普通用户可以发现会员作品并看到会员标识和购买入口，但不能获得会员分区、内容单元、媒体地址和分发能力。
8. 三级权限字段及继承顺序已经冻结：内容单元显式值优先，其次分区、作品，最终默认为 `public`。
9. 4GB 视频链路已由过往项目验证通过，当前项目只需在 Staging 完成环境冒烟回归。
10. 管理后台通过 Telegram 内管理员专用 Web App 登录；管理员本地生成图片浏览版本和缩略图，VPS 不转码。
11. MVP 容量、SLO、RPO、RTO、日志与行为事件保留期以第 15、16 节为验收基线。
12. 锁定作品的会员入口跳转 Bot 内开通说明或人工服务流程，管理员手动开通会员；MVP 不实现订单和支付。
