## 2. 目标与范围

第二期在保持现有 Telegram 存储和播放架构不变的前提下，解决以下问题：

1. 允许管理员通过 Telegram 私有存储频道提交 EPUB，并将其转换为现有漫画阅读器可使用的章节和图片资源。
2. 阻止普通文件或空漫画章节绕过发布校验，保证用户打开的已发布内容一定可消费。
3. 降低图片、漫画和写真批量入库、排序、审核与发布的人工成本。
4. 补齐长列表、历史入口、失败重试、资源健康检查和发布预览等运营闭环。
5. 建立覆盖用户、管理员、Bot、入库任务和真实 Telegram 环境的验收体系。

第二期不改变以下已确认原则：

- 视频继续由 Bot 使用 `copyMessage + protect_content` 发送到用户私聊，并使用 Telegram 原生播放器。
- VPS 不永久保存视频或图片源文件；媒体的长期存储仍由 Telegram 私有频道承担。
- 图片源文件不通过 Bot 或 Mini App 提供给用户。
- 普通用户可以发现会员作品的安全基础资料和会员标识，但不能获得会员目录明细或媒体访问能力。
- 漫画作品不包含视频；没有实际已发布内容的分区不显示。

现有代码已经覆盖“发现作品 -> 查看详情 -> 阅读图片或请求视频 -> 收藏/回访”的核心闭环，可作为非 EPUB 内容的 MVP 使用。影响规模化运营的主要问题是长列表截断、旧历史入口失效、失败恢复不足和缺少真实客户端端到端测试。EPUB 当前没有用户可用能力。

### 6.1 已确认的文件显示缺陷

Bot 在 `apps/bot-worker/src/main.ts` 中将非图片、非视频文档写为 `type: "file"`，而管理台 `apps/admin/src/App.tsx` 的标签函数判断的是 `"document"`。因此 EPUB 等普通文件在待入库列表中可能显示为“未知”，入库抽屉也会使用图片占位图标。该缺陷列为第二期 P0，不等待 EPUB 解析功能一起上线。

### 6.2 管理员体验结论

当前管理台能完成少量作品的人工入库和发布，但不适合长篇漫画或大批量图集。最大的效率瓶颈是逐页创建三种图片版本、手工填写逻辑资源 ID 和页序；最大的完整性风险是文件型资源与漫画可消费资源没有在发布校验中严格区分。

## 8. EPUB 当前能力与问题

### 8.1 当前结论

当前项目只能把 EPUB 当作 Telegram 普通文件登记，不能识别其 EPUB 语义，也不能生成用户可阅读内容，因此 EPUB 功能状态为“缺失”，并非“部分可用”。

### 8.2 代码层问题清单

1. **识别缺失**：未根据扩展名、MIME、ZIP 文件头和 EPUB `mimetype` 条目联合识别。
2. **结构解析缺失**：未解析 `META-INF/container.xml`、OPF Package、Manifest、Spine、EPUB 3 Navigation 或 NCX。
3. **元数据提取缺失**：未提取书名、作者、语言、出版信息、封面、阅读方向和版式。
4. **章节生成缺失**：未把目录和 Spine 映射为漫画分区、章节及页序。
5. **图片处理缺失**：未提取页面图片，也未生成现有发布规则要求的 `source`、`browse`、`thumbnail` 三版本。
6. **任务模型缺失**：无导入任务、步骤进度、错误码、幂等、取消、重试和中间产物清理记录。
7. **管理员流程缺失**：待入库项没有“作为 EPUB 导入”、目录预览、章节合并/拆分或导入结果审核入口。
8. **用户链路缺失**：Mini App 漫画阅读器只接受图片 Manifest，不读取 EPUB、XHTML、CSS、字体或脚本。
9. **类型显示错误**：Bot 写入 `file`，管理台以 `document` 判断文件类型。
10. **发布完整性风险**：发布校验只要求内容单元存在任意可用媒体；可用的 EPUB `file` 可能被视为有效媒体，但用户端无法生成任何漫画页。
11. **文件获取能力缺失**：现有视频链路只复制 Telegram 消息，不下载文件；EPUB 必须实际取得文件字节才能解包。
12. **安全边界缺失**：无 ZIP 炸弹、路径穿越、实体扩展、超大图片、恶意 SVG/HTML、加密内容和 DRM 检查。
13. **测试语料缺失**：无 EPUB 2/3、固定布局、可重排、RTL、NCX/Nav、损坏包、加密包和超大包测试集。

## 9. EPUB 首期产品决策

### 9.1 支持范围

首期支持：

- 无 DRM、无密码的 EPUB 2 或 EPUB 3。
- 以图片为主要页面内容的漫画 EPUB。
- 固定布局 EPUB，或可以确定性提取连续图片页的简单 XHTML EPUB。
- EPUB 3 Navigation 与 EPUB 2 NCX 目录。
- LTR 和 RTL 阅读方向。
- 有目录时按目录生成章节；无目录时按 Spine 提供自动分章建议，并允许管理员调整。

首期暂不支持：

- Adobe DRM、Readium LCP 或其他加密内容。
- 主要内容为可重排文本、复杂 CSS 排版、竖排文本或交互脚本的电子书。
- 依赖 JavaScript、音频、视频、远程资源或复杂 SVG 才能完整展示的 EPUB。
- 在 Mini App 中直接运行 EPUB 的 HTML、CSS 或 JavaScript。
- 用户下载原 EPUB。

不支持的文件必须给出明确原因并保持为未发布状态，不得静默丢页或降级为可发布漫画。

### 9.2 用户端策略

EPUB 仅作为管理员导入源，不作为用户端交付格式。导入服务将其转换为现有图片章节和三版本页面资源；用户仍使用当前漫画阅读器。该方案有以下优点：

- 不需要在 Mini App 中执行 EPUB 内嵌 HTML/脚本，降低安全风险。
- 保持图片签名、会员权限、阅读进度和源文件保护逻辑不变。
- 同一套阅读器覆盖手工入库漫画与 EPUB 导入漫画。
- 运行时不需要再次下载或解包 EPUB。

其代价是导入时需要临时磁盘、图片处理时间和将每页资源回传 Telegram 的带宽。

## 10. EPUB 目标导入流程

```text
管理员向私有频道发送 EPUB
  -> Bot 登记普通文件
  -> 管理台识别 EPUB 候选并发起导入
  -> 导入 Worker 获取文件到隔离临时目录
  -> 文件签名、ZIP 安全和 DRM 预检
  -> 解析 container / OPF / manifest / spine / nav / NCX
  -> 提取元数据、封面、目录、阅读方向和页面顺序
  -> 生成章节草稿及导入预览
  -> 管理员确认章节拆分、标题、页序和作品资料映射
  -> Worker 生成 source / browse / thumbnail
  -> 将页面资源上传回 Telegram 私有频道
  -> 创建草稿分区、章节和媒体关联
  -> 管理员使用用户视角预览
  -> 通过发布校验后发布
  -> 删除 VPS 临时文件并保留导入审计
```

### 10.1 文件识别

识别不能只依赖文件名。候选文件至少执行四层判断：

1. 文件名扩展名为 `.epub`，只作为弱信号。
2. MIME 为 `application/epub+zip`，只作为弱信号。
3. 文件头为 ZIP，且归档根目录存在 `mimetype`。
4. `mimetype` 内容严格为 `application/epub+zip`，并能从 `container.xml` 定位有效 OPF。

前两项用于管理台提前显示“EPUB 候选”，后两项在 Worker 下载后决定是否允许解析。

### 10.2 文件获取适配器

EPUB 与视频复制不同，必须下载字节。实现前先用代表性文件验证当前 Telegram Bot API 的 `getFile` 下载上限和超时。文件获取层应抽象为可替换适配器：

1. 小文件优先使用当前 Bot API 获取。
2. 超出云端 Bot API 下载边界时，采用独立的本地 Bot API 服务、受控 MTProto 下载服务或管理员直传临时导入端点。
3. 无论使用何种方式，长期源文件仍保留在私有频道；VPS 仅保存任务期间的临时副本。
4. 获取失败必须记录 Telegram 错误码、可重试性和已下载字节，禁止无限重试。

在完成真实大文件获取验证前，不承诺“私有频道内任意大小 EPUB 均可自动导入”。

### 10.3 解析与章节映射

- 以 OPF Manifest 确认资源，以 Spine 确认默认阅读顺序，以 Nav/NCX 提供章节边界和标题。
- Nav/NCX 与 Spine 不一致时，以 Spine 保证页面不乱序，并向管理员显示目录告警。
- 固定布局的单页 XHTML 应提取其主图片；一页包含多个候选图片时标记为需要确认。
- 无目录时默认按 Spine 连续顺序生成一个章节，并提供按文件夹、文件名前缀或页数分章建议。
- 封面只作为封面候选，不自动复用为第一幅漫画正文。
- CSS 背景图、SVG 内嵌图和远程资源首期不做无提示转换；应明确标为不支持或需人工处理。
- 图片排序使用解析后的 Spine/DOM 顺序生成，不能仅按压缩包文件名排序。

### 10.4 图片产物

每个可发布页面必须生成并关联：

- `source`：从 EPUB 提取的原始页面图片，以文档方式保存至私有频道，仅供管理和再处理。
- `browse`：满足现有图片代理和发布约束的浏览版，最大 10MB，限制尺寸与宽高比。
- `thumbnail`：目录和快速浏览使用的小图。

三个版本共享同一逻辑资源 ID，并具有从 0 开始、连续、唯一的章节内页序。原 EPUB 文件作为作品级“导入源”保存，不计入用户可消费媒体，也不能单独满足章节发布条件。

## 11. EPUB 导入任务与数据建议

### 11.1 导入任务

新增独立导入任务实体，至少记录：

- 源入库项、Telegram 聊天 ID、消息 ID、文件 ID 和文件唯一 ID。
- 内容 SHA-256、文件大小、检测 MIME、EPUB 版本和版式。
- 当前状态、进度、当前步骤、错误码、错误详情和重试次数。
- 解析出的书名、作者、语言、阅读方向、封面候选、章节数和页数。
- 目标作品、分区、创建方式、管理员调整结果和发布关联。
- 临时目录标识、生成资源数量、上传消息 ID 和清理状态。
- 创建人、确认人、时间戳、请求 ID 和审计信息。

建议状态机：

```text
detected -> queued -> downloading -> validating -> parsing -> awaiting_review
         -> processing -> uploading -> draft_created -> ready_for_preview
         -> completed

任一步骤 -> failed / cancelled
failed -> queued（满足重试条件时）
```

外部 Telegram 上传不是数据库事务，任务必须记录每个已生成消息 ID。失败、取消或重试时根据清单复用已有产物或清理孤儿资源，避免重复上传。

### 11.2 暂存与正式内容隔离

解析结果应先进入导入暂存区，不直接写成已发布内容。管理员确认后再创建或更新正式草稿：

- 新建作品：映射 EPUB 元数据到作品选填字段，保留人工修改能力。
- 已有作品：选择目标漫画目录，避免自动覆盖现有章节。
- 同名章节或重复内容：以内容哈希和源文件唯一 ID 提示重复，由管理员决定跳过、替换或新增。
- 发布前：所有分区、章节和媒体默认保持草稿/待确认状态。

## 12. EPUB 管理员体验

### 12.1 待入库列表

- 普通文件正确显示为“文件”，EPUB 弱识别后显示“EPUB 候选”。
- 提供“作为 EPUB 导入”“作为普通文件处理”“忽略”三个明确操作。
- 显示文件名、大小、MIME、频道消息、检测状态、重复提示和失败原因。

### 12.2 导入向导

向导分为以下步骤：

1. 文件预检：格式、大小、DRM、页面数、风险和预计临时空间。
2. 作品映射：新建作品或选择已有漫画作品。
3. 元数据确认：书名、作者、语言、封面、标签、地区和年份均可调整。
4. 章节编排：预览目录、合并/拆分章节、修改标题、拖动排序和排除页面。
5. 处理进度：展示下载、解析、图片生成和上传的独立进度及失败项。
6. 结果审核：按章节抽查首尾页、封面、顺序、RTL/LTR 和缺页告警。
7. 创建草稿：生成正式草稿后进入现有作品编排，不自动发布。

### 12.3 批量操作

第二期应同时补齐图片运营的通用批量能力：

- 批量选择媒体并关联目标章节。
- 自动生成逻辑资源 ID 和连续页序。
- 批量设为可用、批量撤回、批量重排。
- 批量生成 browse/thumbnail。
- 按失败原因筛选并重试可恢复任务。
- 用户视角预览后一次确认草稿，不逐页重复填写相同字段。

## 13. EPUB 用户体验

首期 EPUB 导入完成后，用户不需要知道源文件格式：

- 作品仍按“漫画”展示。
- 章节目录由导入结果生成，只显示已发布且有权限的章节。
- 阅读器继续支持连续/分页、单双页、LTR/RTL 和进度恢复。
- 原 EPUB、原图、导入路径和私有频道信息不进入用户 DTO。
- 导入失败或尚未完成的章节不显示。
- 若发布后检测到资源失效，只禁用受影响章节并展示可理解的暂不可用状态，不返回源文件。

文本型 EPUB 直接阅读器只有在后续明确产生电子书阅读需求时再立项；届时需单独设计字体、文本选择、搜索、标注、CSS 隔离、脚本禁用和内容安全策略。

## 14. 安全、资源与兼容性要求

### 14.1 归档安全

- 在隔离临时目录解包，拒绝绝对路径、`..` 路径穿越、符号链接和设备文件。
- 限制压缩条目数、单条目大小、总解压大小和压缩比，防止 ZIP 炸弹。
- XML 解析禁用外部实体、DTD 网络访问和实体递归扩展。
- 拒绝加密 ZIP 条目、已知 DRM、远程资源依赖和可执行内容。
- SVG、HTML、CSS 和脚本只用于受控解析，不直接回传浏览器执行。
- 图片处理限制像素数、内存、耗时和并发，损坏图片单独报告。

### 14.2 临时存储

- VPS 仅在任务期间保存源 EPUB、解包内容和待上传图片。
- 任务完成、失败或取消后都必须进入可重试清理流程，并记录清理结果。
- Worker 启动时扫描超时临时目录和孤儿任务，但不删除仍有活动租约的任务。
- 磁盘达到高水位时暂停接收新任务，不能挤占 API、数据库或 Redis 的运行空间。
- 文件名和临时目录使用服务端生成 ID，不使用 EPUB 内部路径作为宿主机路径。

### 14.3 容量建议

EPUB 图片处理不应与当前 API/Bot Worker 共用小规格生产节点。首期建议独立 Worker 起步规格：

| 资源     | 建议起步值 | 说明                                        |
| -------- | ---------: | ------------------------------------------- |
| CPU      |     2 vCPU | 单任务图片转换，避免与在线请求争抢          |
| 内存     |        4GB | 图片解码、压缩和 ZIP 解析；必须设置进程上限 |
| 临时磁盘 |       40GB | 容纳源包、解压结果和三版本待上传文件        |
| 并发     |  1 个 EPUB | 先用队列保证稳定，再根据观测扩容            |

实际规格以最大允许 EPUB、最大总解压量、最大页面像素和同时导入数计算。上线前在目标节点重新测量磁盘余量；若同机部署，预检必须阻止临时空间不足的任务。

### 14.4 Telegram 兼容性

- 验证云 Bot API、本地 Bot API 或 MTProto 获取适配器的实际大小上限和稳定性。
- 页面资源上传需限速、可续传/可恢复，并尊重 Telegram `retry_after`。
- 记录每个上传消息的频道与消息 ID，不能只保留最后一次任务状态。
- 使用代表性的 Telegram iOS、Android、Desktop 和 WebView 客户端验收阅读结果。

## 15. 发布校验调整

第二期 P0 必须将“存在媒体”改为“存在该内容单元可消费的完整媒体”：

1. 漫画章节至少有一组完整、可用且页序合法的图片三版本；普通 `file` 不计数。
2. 图集/写真图片单元至少有一组完整图片；视频花絮按视频规则单独校验。
3. 视频单元至少有一个可用视频，普通文件或图片不能替代。
4. EPUB 源文件只能作为导入来源或作品级管理资源，不能直接发布给用户。
5. 已发布漫画章节的图片 Manifest 为空时必须拒绝发布。
6. 发布校验通过后，以普通用户和会员用户分别请求一次目录/Manifest 作为自动冒烟。
7. 错误信息返回稳定错误码、可读说明和可定位路径，管理台可直接跳转到对应章节或资源。

## 16. 第二期工作包

### WP0：内容完整性与现有缺陷（P0）

- 修复 `file` / `document` 类型显示不一致。
- 收紧类型化发布校验，阻止 EPUB 文件或其他普通文件让空漫画通过校验。
- 增加 Manifest 为空、缺少图片版本、页序错误和错误类型的契约测试。
- 修复分类最多 40 项和历史记录依赖最近作品集合的问题。
- 为失败视频发送提供明确原因和可控重试入口。

**完成标准**：任何已发布单元都能由对应用户端消费；长列表和旧历史记录不再因固定批次截断。

### WP1：EPUB 技术验证与样本库（P0）

- 建立去敏测试语料：EPUB 2/3、Nav/NCX、固定布局、图片型、RTL、无目录、损坏、加密和超大包。
- 验证 Bot API 文件获取上限，确定大文件获取适配器。
- 比较成熟 EPUB/ZIP/XML 解析库，避免手写 ZIP 和 XML 解析器。
- 测量页数、图片像素、CPU、内存、磁盘、上传耗时和 Telegram 限流。
- 冻结首期最大文件、最大解压量、最大页数、最大像素及超时配置。

**完成标准**：至少 20 个代表性样本形成可重复验证报告，所有限制有实测依据。

### WP2：导入 Worker 与任务状态机（P1）

- 新增导入队列、任务状态、租约、幂等、进度、错误分类和取消/重试。
- 实现受控下载、临时目录、ZIP/XML 安全预检和超时清理。
- 解析元数据、OPF、Manifest、Spine、Nav/NCX、阅读方向和封面。
- 生成章节建议和暂存结果，不直接发布。

**完成标准**：Worker 重启、网络中断或重复提交后可以继续或幂等重试，不产生重复正式章节。

### WP3：图片处理与 Telegram 回传（P1）

- 提取原始页面并生成 source、browse、thumbnail。
- 实施图片 MIME、尺寸、大小、方向和损坏检查。
- 逐页上传私有频道，记录消息 ID，处理限流和部分失败。
- 为内容哈希相同的页面提供去重提示，不自动跨作品复用权限资源。

**完成标准**：成功导入的每页都有完整三版本、连续页序和可验证 Telegram 来源；临时文件全部可追踪清理。

### WP4：管理员 EPUB 向导与批量编排（P1）

- 待入库候选识别、导入向导、目录预览、章节调整和进度页面。
- 批量关联、排序、状态变更和失败重试。
- 新建/已有作品映射、元数据填充、封面候选和重复内容提示。
- 用户视角预览、发布错误定位和发布后自动冒烟。

**完成标准**：管理员无需逐页填写 UUID 和页序，即可把合规 EPUB 转换为可预览草稿并完成发布。

### WP5：运营和资源治理（P1）

- 待入库忽略/拒绝/重试状态与筛选。
- 定期检查存储频道资源有效性、重复文件和数据库一致性。
- 队列积压、失败率、处理耗时、临时磁盘和 Telegram 限流告警。
- 管理台增加失败任务、资源健康和发布后检查视图。

**完成标准**：常见故障可由管理员定位和恢复，不依赖直接查数据库或容器日志。

### WP6：用户与增长闭环（P2）

- 推荐内容的运营置顶、屏蔽、质量指标和实验版本。
- 会员订单、支付、续费和到期提醒在单独产品决策后实施。
- 用户数据导出、账号删除申请、历史清理和隐私说明。

### WP7：后续 EPUB 扩展（P3）

- 文本型、可重排 EPUB 阅读器。
- 全文搜索、字体、字号、主题、标注和书签。
- 复杂 CSS、竖排、SVG、脚注和无障碍语义。

此工作包不作为第二期首发阻断项。

## 18. 测试矩阵

### 18.1 EPUB 格式

- EPUB 2 + NCX、EPUB 3 + Nav。
- 固定布局、简单图片 XHTML、LTR、RTL。
- 单章节、多章节、无目录、目录与 Spine 不一致。
- JPG、PNG、WebP、GIF、SVG 候选及混合图片格式。
- 无封面、多封面候选、缺图、重复页、损坏图片和错误 MIME。
- ZIP 路径穿越、ZIP 炸弹、加密条目、DRM、XML 外部实体和远程资源。
- 文件名含中文、空格、特殊字符和大小写混合扩展名。

### 18.2 任务可靠性

- 重复提交、并发提交、Worker 重启、下载中断、上传中断和数据库短暂不可用。
- Telegram 限流、频道权限丢失、源消息删除、部分页面上传成功。
- 取消、重试、清理失败、孤儿临时目录和孤儿频道消息。
- 磁盘高水位、内存限制、超时和超大像素图片。

### 18.3 权限与发布

- 公开、会员和继承权限覆盖作品、分区、章节三级组合。
- 普通用户只能看到会员作品的安全基础资料，不得到 EPUB、原图、章节明细或媒体签名。
- 普通文件、空 Manifest、缺版本、断序和错误媒体类型全部阻止发布。
- 用户视角预览与实际发布结果一致。

### 18.4 客户端

- Telegram iOS、Android、Desktop 及目标 WebView。
- 小屏手机、平板、横竖屏、弱网和断网恢复。
- 超长章节、连续滚动、单双页、LTR/RTL 和进度恢复。

## 19. 首期 EPUB 验收标准

全部满足后，EPUB 导入功能才可标记为完备：

1. 合规样本可以稳定识别，非 EPUB、损坏、DRM 和超限文件得到明确结果。
2. 章节、页序、封面和阅读方向与基准阅读器一致；不允许静默缺页。
3. 每个正式漫画页具有完整三版本，原 EPUB 和原图不进入用户响应。
4. 导入默认创建草稿，管理员完成预览后才能发布。
5. 任务可取消、可重试、可恢复；重复操作不创建重复章节或重复正式资源。
6. 失败和完成后的临时文件清理均有记录，超时任务有自动回收机制。
7. 普通文件或空漫画章节无法通过发布校验。
8. 普通用户、会员和管理员权限测试全部通过，无私有频道 ID、文件 ID 或源资源泄漏。
9. 代表性最大文件在目标 Worker 上完成容量和性能测试，API 与视频 Bot 服务不受明显影响。
10. 管理员无需逐页录入 UUID 和页序即可完成一本合规漫画的导入、调整、预览和发布。
11. 自动化单元、数据库集成、任务故障恢复和前端端到端测试进入 CI。
12. Staging 真实 Telegram 上传、下载、回传和多客户端阅读验收通过。

## 20. 风险与回滚

| 风险                    | 影响                 | 处理与回滚                                                     |
| ----------------------- | -------------------- | -------------------------------------------------------------- |
| Bot API 无法下载大 EPUB | 导入无法开始         | M1 实测并切换获取适配器；未通过前只开放已验证大小              |
| EPUB 结构差异大         | 章节错误或缺页       | 限定首期格式、提供预览和不支持原因，禁止自动发布               |
| ZIP/图片资源耗尽        | Worker 或主机不可用  | 独立 Worker、硬限制、单并发、高水位暂停和任务超时              |
| Telegram 上传限流       | 导入耗时长或部分失败 | 节流、断点记录、指数退避和基于消息 ID 的幂等恢复               |
| 外部上传与数据库不一致  | 孤儿消息或重复资源   | 产物清单、补偿清理、重复哈希检测和审计                         |
| 错误发布泄漏源资源      | 内容保护失效         | EPUB/源图永不进入用户 DTO，发布校验和权限测试双重阻断          |
| 新导入影响现有阅读器    | 已有漫画回归         | 输出保持现有图片 Manifest 契约，功能开关灰度，关闭入口即可回滚 |
| 数据迁移影响旧版本      | 发布回滚困难         | 使用向前兼容的扩展迁移；先部署读取兼容，再启用导入功能         |

回滚以功能开关为第一手段：停止新 EPUB 导入、保留现有成功生成的标准图片章节，暂停失败任务并清理临时文件。已发布且通过现有 Manifest 验证的章节无需因关闭 EPUB 导入而下架；异常章节按资源健康检查结果单独撤回。

## 21. 第二期完成定义

第二期达到发布条件需同时满足：

- WP0-WP5 全部达到各自完成标准。
- EPUB 首期验收标准 12 项全部通过并形成可追溯记录。
- 核心用户闭环、管理员导入发布闭环和 Bot 视频闭环均有端到端测试或真实环境验收证据。
- 资源失效、任务失败、Telegram 限流、磁盘高水位和 Worker 重启均有可执行恢复流程。
- 生产状态文档统一，README、需求、技术文档、运行手册和验证记录不再互相矛盾。
- 发布采用独立版本标签，发布前完成备份，灰度期间监控错误率、任务耗时、队列积压和磁盘水位，并验证回滚。

## 22. 开发建议摘要

1. **先修发布完整性，再做 EPUB**：否则导入工作会放大当前普通文件可绕过媒体校验的风险。
2. **先实测文件获取，再定工期**：Telegram 消息复制成功不代表可以下载并解析同样大小的 EPUB。
3. **EPUB 作为导入源，不作为用户格式**：首期复用现有漫画阅读器是成本、体验和安全最平衡的方案。
4. **使用独立 Worker**：解包和图片转换属于高 CPU、内存、磁盘任务，不应阻塞在线 API 或视频 Bot。
5. **把批量能力作为同一项目交付**：仅增加解析器但保留逐页人工审核，无法真正解决管理员录入效率。
6. **默认草稿和人工确认**：EPUB 目录质量差异大，任何自动结果都不得绕过管理员预览与发布校验。
7. **扩大测试重心**：当前工程测试偏基础契约，第二期必须加入数据库集成、任务恢复、前端 E2E 和真实 Telegram 验收。
